## 1. 全体の形

3つのプロセスが1つのデータディレクトリと2つのデータベースを共有する。

```
                    ┌──────────────────────────────┐
   Discord  ───────▶│  Bot            main.py      │
                    │  イベント / コマンド / 定期   │
                    └───────┬──────────────┬───────┘
                            │              │
            ┌───────────────┴──┐        ┌──┴──────────────────┐
            │  /app/data       │        │  Postgres           │
            │  settings.json   │        │  metal_prices       │
            │  _dev_signals/   │        │  user_state_audit   │
            │  djaudio_cache/  │        └──┬───────────┬──────┘
            │  logs/           │           │           │
            │  _recording_...  │           │           │
            └───────────────┬──┘           │           │
                            │              │           │
   ブラウザ ───────▶┌───────┴──────────────┴───┐       │
                    │  Admin UI  admin_main.py │ :5001 │
                    │  設定 / 監視 / SQL /      │       │
                    │  ミキサー / 配信(/dlaudio)│       │
                    └──────────────────────────┘       │
                                                       │
   ブラウザ ───────▶┌──────────────────────────────────┴┐
                    │  Web App          web_main.py     │ :8000
                    │  貴金属トラッカー（公開 PWA）      │
                    └───────────────────────────────────┘
```

| プロセス | 入口 | 役割 |
|---|---|---|
| Bot | `main.py` → `bot_setup.py` | Discord のイベント処理、スラッシュコマンド、定期タスク |
| Admin UI | `admin_main.py` → `webapp_admin/app.py` | 設定画面、監視、SQL エディタ、録音ミキサー、`/dlaudio` の配信 |
| Web App | `web_main.py` → `webapp/app.py` | 貴金属価格トラッカー（公開 PWA）、週次予測、Web Push |
| CDN（任意） | `cdn_main.py` | `/dlaudio` だけを別プロセスで受け持つ。管理画面と同じルータを載せる |

`docker-compose.yml` で立つのは上の3つと Postgres、それに初期化ジョブが2つ
（`postgres-secret-init` がパスワードを生成し、`postgres-user-state-init` が
監査用データベースを作る）。`cdn_main.py` は配信を分離したいときの選択肢で、
既定の構成では管理画面が `/dlaudio` を持つ。

### なぜプロセスを分けるか

Bot は Discord のゲートウェイに常時つながっていて、落とすと再接続に時間が
かかる。管理画面の再起動や重いクエリで Bot を巻き込みたくない。逆に、
Discord へ送る・VC へ繋ぐといった操作は Bot にしかできない。そこで
**「状態は共有し、操作はシグナルで頼む」**形にしている（→ [3節](#3-プロセス間の連携)）。

Web App（貴金属トラッカー）は Discord を知らない。公開ページなので、Bot や
管理画面の都合で落ちてほしくない。`metal_prices` を読み書きするのは Web App
だけで、Bot はそこを見ない（Bot の `/metal` は `services/metal_service.py` から
MetalpriceAPI を直接引く。Web App の日次スナップショットも同じモジュールを
通るので、価格の取り方は1箇所にまとまっている）。

### 依存の向き

```
  commands/  ──▶  services/  ──▶  config.py, envutil.py
                     ▲
  bot_setup.py ──────┘

  webapp_admin/  ──▶  services/       （設定の読み書きと配信ルータ）
       │
       └──▶  webapp_admin/schema/  ──▶  services/

  webapp/  ──▶  envutil.py, config.py
       └──▶  services/ のうち3つだけ（下記）
```

Web App が `services/` から借りているのは、**どのプロセスから呼んでも同じで
あるべきもの**に限っている。

| 借りているもの | 理由 |
|---|---|
| `services/url_safety.py` | 外から取った URL の検査を1箇所にまとめたい |
| `services/metal_service.py` | 価格の取り方（API・キャッシュ）を Bot と揃えたい |
| `services/groq_client.py` | Groq のレート制御を全機能で共有したい（→ 13節） |

逆向き（`services/` が `webapp/` を見る）は無い。ただし SQL エディタだけは
両方の DSN を一覧するために `webapp.db` と `services.user_state_db` を
遅延 import する。

`envutil.py` は**標準ライブラリしか使わない**。bot / webapp / webapp_admin の
どこからでも副作用なしに import できることを意図している（`config.py` は
import 時に ffmpeg の解決をするので、共通の置き場にはできない）。

## 2. 状態をどこに置くか

### 2.1 データディレクトリ

| 置き場 | 中身 | 読み書きする側 |
|---|---|---|
| `data/settings.json` | ギルドごとの全設定 | Bot / Admin（`services/settings_store.py` 経由） |
| `data/settings.json.lock` | 書き込みの排他 | 同上 |
| `data/_dev_signals/` | Bot への依頼（→ 3節） | Admin が書き、Bot が読む |
| `data/djaudio_cache/` | 配信するファイルと `<token>.json` のメタ | Bot が書き、`/dlaudio` が読む |
| `data/_recording_state.json` | 録音中の状況 | Bot が書き、Admin が読む |
| `data/admin_monitor/heartbeat.json` | 管理画面の死活 | Admin |
| `data/.admin_session_secret` | セッション署名キー | Admin（無ければ生成する） |
| `data/logs/` | 各プロセスのログ（`RotatingFileHandler`） | それぞれ |

`data/` は Docker のボリューム `app_data` として3つのコンテナすべてに
`/app/data` でマウントされる。場所の解決は必ず `SETTINGS_DIR` を通す。

### 2.2 Postgres

**`metal_prices`**（Web App が所有）

| テーブル | 中身 |
|---|---|
| `metal_price_daily` | 日次スナップショット（金・銀・プラチナの円/g） |
| `weekly_forecast_meta` | 週次予測1回ぶんのメタ（モデル種別、為替の出所、材料） |
| `weekly_forecast_daily` | その予測の日ごとの中心値と区間 |
| `forecast_accuracy_log` | 答え合わせ用。予測・実勢・区間に入ったか・ベースライン |
| `push_subscription` | Web Push の購読 |
| `notification_dispatch` | 通知の送信記録（重複送信を防ぐ） |

**`user_state_audit`**（Bot と Admin が共有）

| テーブル | 中身 |
|---|---|
| `user_state_current` | ユーザーごとの現在の状態（在籍 / 退出 / BAN 済み、ロール、権限） |
| `user_state_event` | 状態が変わった出来事の履歴（参加・退出・BAN・KICK・ロール変化） |

スキーマの変更は Alembic（`migrations/versions/`）。現在 0001〜0005。

`user_state_audit` は Bot が起動時に `ensure_user_state_db()` でテーブルを
作るので、マイグレーションを回さなくても立ち上がる。これは Bot だけを
別ホストで動かす構成のためで、`metal_prices` 側は Web App が `init_db()` で
同じことをする。

### 2.3 settings.json をデータベースに置かない理由

設定は「ギルドごとの入れ子の辞書」で、更新は人の操作の速さでしか起きない。
それに対して読み出しはメッセージのたびに走る。ファイル＋メモリキャッシュに
しておくと、DB を1つ増やさずに済む。

キャッシュの無効化は**ファイル署名（`mtime_ns` + `size`）**で行う。署名が
変わったら捨てて読み直すので、Bot と管理画面が別プロセスでも相手の更新に
気づける。

書き込みはロックファイル（`O_CREAT | O_EXCL`）で直列化する。ロックを持った
まま死んだ場合に備えて、`SETTINGS_LOCK_STALE_SECONDS`（既定30秒）を過ぎた
ロックは奪える。解放時は**自分が書いた所有者IDと一致するときだけ**消す
（他人のロックを消さないため）。

JSON の読み書きは `orjson` があればそれを使い、無ければ標準の `json` に落ちる。

## 3. プロセス間の連携

### 3.1 シグナル（Admin → Bot）

管理画面から「録音を開始」「通知をテスト送信」を押したとき、その処理は Bot に
しかできない。共有ディレクトリにファイルを1つ置き、Bot が30秒ごとに拾って
実行する。実装は `services/dev_signals.py`。

```
Admin  ──▶  data/_dev_signals/recording_start.<一意>.signal  ──▶  Bot
                        （payload に guild_id / channel_id）
```

ファイル名の付け方に意味がある。

| 形 | 用途 | 例 |
|---|---|---|
| `<用途>.signal` | 何度実行しても結果が同じもの。溜める意味が無いので上書き | `news_feeds`, `sticky`, `djaudio_cache`, `earthquake_reconnect`, `user_state_repair` |
| `<用途>.<一意>.signal` | 対象が payload の中にしかないもの。上書きすると別の対象宛が消える | `recording_start`, `recording_stop`, `eq_replay`, `test_*` |

後者を用途名だけで書いていたときは、2つのサーバーの管理者が30秒以内に操作
すると先の1件が黙って消えていた。押した側には「キューに追加しました」と出た
ままで、ログにも残らない。Bot 側は「最初の `.` まで」を用途名として読むので、
どちらの形も同じ分岐に落ちる。処理は**置かれた順**（mtime）で行う。開始と
停止が入れ替わると噛み合わないため。

どの分岐にも当たらなかったシグナルは、必ず warning を出す。黙って消えると
「受信」「完了」のログだけが残り、何も実行されないまま成功に見える。

**制約**: 反映まで最大30秒。押した瞬間に結果は返らないので、UI は
「キューに追加しました」と伝えて状況を数秒おきに取り直す。即時性が要る操作を
ここに載せてはいけない。

### 3.2 状態ファイル（Bot → Admin）

録音中かどうかは Bot のメモリにしかない。管理画面から見えるように、開始・
停止・見張りのたびに `_recording_state.json` へ書き出す（一時ファイルに書いて
`replace` する）。管理画面はこれを読むだけで、Bot に問い合わせない。

### 3.3 スケジューラの重複起動を防ぐ

Web App は複数ワーカーで動く。定期ジョブ（日次スナップショット、予測の更新、
Push 通知）が全ワーカーで走ると多重送信になるので、**Postgres の
session-level advisory lock** を取れたプロセスだけがスケジューラを持つ。

### 3.4 管理画面の複数ワーカー

`ADMIN_WORKERS > 1` にすると、メトリクス（TPS）・監視スレッド・レート制限が
いずれもプロセスローカルなので表示値がズレる。起動時に警告を出し、レート制限
だけは `ADMIN_LIMITER_STORAGE_URI` に Redis を指定すれば共有できるようにして
ある。セッション署名キーはワーカーを spawn する前に env へ確定させる（全ワーカーが
同じキーを継承しないとセッションが壊れる）。

## 4. Bot

### 4.1 構成

```
  main.py            ログ設定、create_bot、コマンド登録、起動
    └─ bot_setup.py  events/ の各 register(bot) を呼ぶだけ（35行）
         └─ events/    イベントハンドラと定期タスク（9モジュール）
    └─ commands/     スラッシュコマンドの登録（機能ごと）
         └─ services/  実処理
```

`commands/__init__.py` が登録モジュールの一覧を持ち、`register_all_commands()`
が順に呼ぶ。増やすときはここに1行足す。

登録関数が大きくなったものは、トピックごとのサブパッケージへ割ってある。
どれも「登録は薄く、中身は素の関数へ」で、呼び出し口の型は変えていない。

| 分割元 | 分割先 | 経緯 |
|---|---|---|
| `setup_events`（1,210行） | `events/` 9モジュール | `events/__init__.py` |
| `register_server_commands`（457行） | `commands/server/` 7モジュール | `commands/server/__init__.py` |
| `register_logging_commands`（271行） | `commands/settings/` 6モジュール | `commands/settings/__init__.py` |
| `register_recording_commands`（268行） | `commands/record/` 3モジュール | `commands/record/__init__.py` |

`commands/server/` は各モジュールが自分でグループを作って
`bot.tree.add_command()` まで行う。`commands/settings/` と `commands/record/` は
そうしていない。前者は5つのグループの登録順を1箇所で読める形を保つため、
後者は6コマンドが1つの `/record` グループを共有していて、そもそも各モジュールが
自分でグループを作れないため。**分け方が3通りあるのは、共有するものが違うから**で、
揃えていないのは意図的。

### 4.2 イベントと定期タスク

| イベント | 主な処理 |
|---|---|
| `on_message` | セキュリティ検査、ChatGPT 応答、DJAudio の URL 検知、スティッキー、TTS |
| `on_message_delete` / `on_message_edit` | 監査ログ |
| `on_voice_state_update` | VC 通知、VCレイド検出、TTS の入退室読み上げ、自動録音、入室時間の記録 |
| `on_member_join` / `on_member_remove` | ウェルカム / グッバイ、状態監査 |
| `on_member_update` | ロール変化の監査 |
| `on_member_ban` / `on_member_unban` | 監査（監査ログから実行者を引く） |
| `on_raw_reaction_add` / `remove` | リアクションロール |

| 定期タスク | 間隔 |
|---|---|
| `update_status` | 20秒（Discord のプレゼンス更新は20秒あたり5回まで） |
| `news_feed_task` | 5分 |
| `pending_sticky_task` | 30秒 |
| `dev_signal_task` | 30秒 |
| 地震 WebSocket | 常時接続（切れたら再接続） |
| ユーザー状態の同期 / 整合性修復 | 起動時 + 30分間隔 |

`_BOT_BACKGROUND_WORKER=false` にすると定期タスクを持たない Bot にできる。
同じ Bot を複数インスタンス立てるときに、片方だけが定期処理を担当する構成が
作れる。

### 4.3 付随処理で本筋を止めない

イベントハンドラごとに `try/except/logger.exception` を書き下すと、定型が
積み上がって本来の分岐が埋もれる（実際 1,200行の相当部分がこれだった）。
`_safe(coro, name)` に1箇所へまとめてある。

### 4.4 スラッシュコマンドの共通処理

`commands/interaction_utils.py` に集約している。

- **`send_interaction`**: `defer()` を挟んだあとに `response.send_message()` を
  呼ぶと失敗する。どちらの経路も通るようにここで吸収する
- **`cap_list_for_message`**: 一覧を**文字数**で打ち切る。件数だけで切ると、
  1件あたりの長さが可変な入力（検索クエリ、辞書の読み）では上限超過を防げない
  （実際に `/news list` で発生した）。Discord の上限は名前を付けて集約して
  ある（`MESSAGE_BUDGET` 2000 / `EMBED_DESCRIPTION_BUDGET` 4096 /
  `EMBED_FIELD_BUDGET` 1024）。省略行（"…他N件"）自身の長さも予算に含める
- **エラーハンドラ**: 権限不足・条件不一致・実行時エラーを、コマンド単位と
  ツリー全体の両方で受ける

権限判定は `commands/guards.py` に2つある。`ensure_admin()` は拒否メッセージを
送るところまでやり、`is_admin()` は返信せずに真偽だけ返す（「権限があれば
追加の処理もする」という分岐に使う）。

## 5. 設定の層

```
  スラッシュコマンド ──┐
                        ├──▶ services/settings_store.py ──▶ settings.json
  管理画面のスキーマ ──┘        services/tts_store.py
                                services/logging_service.py
```

**設定の読み書きは必ず1本の関数を通す。** 管理画面のスキーマは
`settings.json` の構造を知らない。値の出し入れは `Field.get` / `Field.set` が
指す `services/*` の関数に委ねる。Bot 側も同じ関数を読むので、管理画面と Bot で
設定の解釈がズレない。

TTS だけは専用ストア（`services/tts_store.py`）を経由する。`watch_channel_ids`
の int 化など、`settings.json` を直接触ると壊れる整合性がそこに入っている。

設定の既定値も1箇所に置く（例: `_RECORDING_DEFAULTS`）。許容範囲の定数
（`MAX_MINUTES_LIMIT`、`RETENTION_DAYS_MIN/MAX`、`DJAUDIO_LIMITS`）は、管理画面の
バリデーションとスラッシュコマンドの両方が同じものを参照する。片方だけ古いと、
入れられた値が黙って弾かれたり丸められたりする。DJAudio はこれを別々に書いて
いたので、パネル側が保存側の表を読む形に直した。

### 5.1 非同期から設定を書くときは必ずスレッドへ逃がす

`settings.json` の書き込みはファイルロックを取る。空くのを待つ間は
`time.sleep(0.05)` のポーリングで、既定のタイムアウトは10秒
（`SETTINGS_LOCK_TIMEOUT_SECONDS`）。Bot と管理画面は別プロセスで同じファイルを
共有しているので、競合は実際に起きる。

`async` の中から同期のセッターを直に呼ぶと、待つ側のイベントループ全体がその間
止まる。**Bot なら Discord のハートビートと全ギルドのイベント処理が、管理画面
（既定 `ADMIN_WORKERS=1`）ならヘルスチェックを含む全 HTTP 応答が固まる。**

そのため、非同期の文脈からの書き込みは `settings_store.awrite()` を通す。

```python
await awrite(set_welcome_channel, guild_id, channel.id)
```

スキーマ駆動のパネル（`webapp_admin/api/apps.py`）は、どのセッターが呼ばれるかが
実行時に決まるので、保存のループごと `asyncio.to_thread` へ逃がしている。

直呼びは見た目では気付けない（普通の関数呼び出しにしか見えない）ため、構文木から
機械的に見つける検査を置いてある（`tests/test_services.py` の
`SettingsWriteOffloadTests`）。`_mutate_settings` から辿れる公開関数を実装から
その都度求めるので、セッターを増やしても表を更新する必要は無い。仕組みが効いて
いること自体も、実際に待たせて他のコルーチンが進むかで確かめている。

## 6. 管理画面

### 6.1 スキーマ駆動

「管理UIにどんな設定が存在するか」の単一の情報源は
`webapp_admin/schema/panels/*.py` の宣言。ここから、

- フォームの描画（クライアント）
- 入力値の検証（サーバ）
- API の受け口
- スタートメニューのタイルと並び順
- `docs/ADMIN.ja.md` の設定表（`tools/generate_admin_docs.py` が生成）

がすべて派生する。個別に定義しない。設定を1つ増やすときに触るのは宣言と
`services/*` の get/set だけで、画面・検証・ドキュメントは付いてくる。

型は `schema/types.py` にある。

| 型 | 役割 |
|---|---|
| `Panel` | 1画面。ID・題・アイコン・グループ・窓の大きさ・旧URL |
| `Section` | パネル内の区切り |
| `Field` | 設定1項目。`widget` / `get` / `set` / `default` / `min` / `max` / `help` |
| `Collection` | 一覧（ニュースフィード、辞書など）。`list` / `add` / `remove` |
| `Widget` | 入力欄の種類。`TEXT` `TEXTAREA` `INT` `DURATION` `BOOL` `SELECT` `CHANNEL` `VOICE_CHANNEL` `ROLE` `CHECKLIST` `SNOWFLAKE` |
| `ChoiceSource` | 実行時に解決する選択肢の供給元。`CHANNELS` `VOICE_CHANNELS` `ROLES` `TTS_VOICES` |

検証（`schema/validation.py`）の規則は**スキーマだけから導く**。画面ごとに
`if` を書き分けない。エラーはフィールド単位で返し、クライアントは該当入力欄の
直下に出す。

選択肢の解決（`schema/choices.py`）は、1リクエストにつき必要な供給元だけを
1回ずつ取得してまとめて返す。**取得に失敗した供給元は空リスト**になり、
呼び出し側は「選択肢が空」を異常ではなく通常の状態として扱う（TTS API 停止時の
声一覧など）。画面はそのとき手入力へ切り替える。

期間（`DURATION`）は保存は秒のまま、入力と表示だけ単位を付ける。30日を秒で
書くと 2,592,000 になり、この桁を利用者に数えさせるのもドキュメントに
「60〜2592000」と載せるのも無理がある。入力欄・エラー文・生成ドキュメントの
三箇所が同じ単位表記を使う（`schema/duration.py`）。

スキーマから描けない画面（監視、SQL エディタ、VC録音、開発者パネル、
ユーザー状態監査）は `schema/panels/custom.py` に「タイルとしての情報」だけを
置き、中身は `static/js/apps/*.js` が専用の API を読んで描く。並び順を1箇所で
管理するため、これらも同じ登録簿に載せる。

### 6.2 バックエンドの構成

```
  webapp_admin/app.py         create_app()。ルータ・ミドルウェア・例外処理
    ├─ views/auth_views.py     Discord OAuth のログイン / ログアウト
    ├─ views/dashboard_views.py デスクトップのシェルとギルド選択（HTML を返すだけ）
    ├─ api/apps.py             スキーマ駆動の設定 API
    ├─ api/users.py            ユーザー状態監査（絞り込み・ページ送りはサーバ側）
    ├─ api/recording.py        VC録音の状況・操作・アーカイブ一覧
    ├─ api/dev.py              開発者パネル（DEV_USER_ID 限定）
    ├─ api/sql.py              SQL エディタ（DEV_USER_ID 限定）
    └─ services/djaudio_cdn.py /dlaudio の配信ルータ
```

`api/apps.py` は画面ごとの action 分岐を持たない。何を受け付けるかは
スキーマの宣言だけが決める。

`api/users.py` は一覧の絞り込みとページ送りをサーバ側で行う。以前は全件を
HTML に描画してからクライアントで分割していて、件数が増えるほど重くなって
いた。表示用のラベル（状態・イベント種別・権限）と JST 整形もサーバでやり、
クライアントは受け取った文字列を並べるだけにする。

### 6.3 JSON に ID を数値で入れない

Discord の ID（スノーフレーク）は19桁ある。JavaScript の数値は 2^53−1
までしか正確に扱えないので、JSON に数値として入れると読み込んだ時点で桁が
落ちる。

```
1234567890123456789  →  1234567890123456800
```

実際にこれで、実在するチャンネルを指定しているのに管理画面のプルダウンが
「一覧にありません」になった。値そのものが別物になっていたため、一覧と
突き合わせても一致しない。`api/jsonsafe.py` の `SafeJSONResponse` が、安全な
範囲を超える整数を文字列にして返す。ID は計算に使わないので文字列で困らない。

### 6.4 認証・認可

- **ログイン**: Discord OAuth。`identify` と `guilds` を取り、Bot が居て
  かつ本人が管理者権限を持つギルドだけを選択肢に出す
- **セッション**: 署名付き Cookie。キーは `ADMIN_FLASK_SECRET_KEY`、無ければ
  `data/.admin_session_secret` を `O_EXCL` で生成する
- **CSRF**: 書き込み系は `X-CSRFToken` ヘッダ必須。トークンはページの
  `<meta name="csrf-token">` に埋め、`lib/api.js` が自動で付ける
- **レート制限**: SlowAPI。エンドポイントごとに個別に掛ける
- **セキュリティヘッダ**: `FLASK_SECURE_COOKIES` で Secure 属性と HSTS を制御
  （値の解釈は `envutil.env_bool` に揃えてある。ここだけ `== "true"` の手書き
  判定だったため `FLASK_SECURE_COOKIES=1` が黙って無効になっていた）
- **権限の再確認**: `user_still_admin()` で、ログイン後に権限が外れていないかを
  確かめる

### 6.5 開発者専用の面

`DEV_USER_ID` に一致するユーザーだけが開発者パネルと SQL エディタを開ける。
**未設定なら 404**（存在しないものとして扱う）。「設定されているか」の判定は
`webapp_admin/security.dev_user_id()` に一本化してある（以前は
`api/dev.py` が `os.getenv` を直に見ていて、`DEV_USER_ID=" "` のときだけ
404 ではなく 403 になっていた）。

**開発者パネル**（`api/dev.py`）:
定期タスクの手動実行、通知テスト、地震イベントのリプレイ、設定の
エクスポート/インポート、ログ閲覧、キャッシュ一覧、環境変数の状態表示
（秘密は先頭4文字だけ）。

通知テストの原則は2つ。**本番と同じ関数・同じ既定値を使う**（テストが本番と
違うものを出すと確認の意味が無い。実際ウェルカムのテストだけ独自の既定文面を
持っていた）。**`channel_id` を指定したら本番のチャンネル設定を一切見ずに
そこへ送る**（本番設定を作らないとテストできない状態にしない）。中身は
`services/dev_test_notify.py` にあり、Bot 側と共有する。

**SQL エディタ**（`api/sql.py`）の安全側の既定:

- 読み取り専用トランザクション。**SQL の文字列判定ではなく** Postgres 側で
  `READ ONLY` を宣言するので抜け道が無い
- 接続先はアプリ自身が持つ DSN のみ。画面から変えられるのは「同じサーバ上の
  データベース名」だけで、ホストや資格情報は差し替えられない
- `statement_timeout` をセッションに設定し、行はサーバ側カーソルで上限まで
- 接続はリクエストごとに開いて閉じる（アプリ本体のプールとは別なので、重い
  クエリで Bot や管理画面を止めない）
- 実行した SQL は利用者IDつきで warning ログに残す
- `VACUUM` のようにトランザクション内で実行できない文は、書き込みモードで
  1文だけ投げられたときに限りトランザクション無しで流す（pgAdmin の自動
  コミットに相当する逃げ道）
- `;` での文の分割は、文字列・引用付き識別子・ドル引用・コメントの中では
  切らない

### 6.6 監視

`metrics.py` がリクエスト数（TPS）、エラー率、SLA、ホストの CPU / メモリを
持つ。背景スレッドが定期的にサンプルを取り、閾値を超えたら「インシデント」
として記録する。`data/admin_monitor/heartbeat.json` に死活を書く。

いずれもプロセスローカルなので、複数ワーカーでは値がズレる（→ 3.4）。

### 6.7 フロントエンド

ビルド工程は無い。素の ES モジュールをそのまま配る。

```
  static/js/
    main.js            起動。タイル一覧を取り、前回の配置を復元し、ディープリンクを開く
    wm/desktop.js      ウィンドウマネージャ。開閉・重なり順・タスクバー・
                       スタートメニュー・配置の保存
    wm/window.js       ウィンドウ本体。移動・リサイズ・最大化・閉じる確認
    wm/specular.js     見た目（光沢）
    forms/panel.js     スキーマからウィンドウの中身を描く
    forms/widgets.js   入力欄の実装
    lib/api.js         管理API の薄いラッパー。CSRF を自動で付ける
    lib/dom.js         el() / clear() / append() など
    lib/tabs.js, toast.js, motion.js, choices.js
    apps/*.js          専用画面（monitor / user_state / dev / sql / recording / mixer）
```

ウィンドウの中身は iframe ではなく DOM。**未保存の変更を持ったまま閉じようと
したら確認できる**ようにするため。

- 設定の変更は**明示保存**（保存ボタンを押すまで反映しない）
- 一覧への**追加・削除は即時**（保存ボタンには含めない）

この2つを混ぜないのは、一覧の操作を保存待ちにすると「追加したのに消える」
事故が起きるため。保存の結果は応答で画面に反映する（リダイレクトもリロードも
しない）。

CSS はトークン（`css/tokens.css`）を土台に、`base` / `components` / `page` /
`desktop` / `motion` / `sql` / `public` に分かれる。アイコンは
bootstrap-icons の2,000個から実際に使うものだけを抜いた SVG スプライト
（`tools/build_icon_sprite.py` で再生成）。CSS/JS は Docker イメージのビルド時に
`scripts/minify_assets.py` が再帰的に圧縮する。

## 7. 音声

### 7.1 接続の共有

Discord の bot は1ギルドにつき音声接続を**1本**しか持てない。読み上げ（送信）と
録音（受信）を同時に使うには、同じ `VoiceClient` を共有するしかない。

```
  TTS ─────┐
           ├──▶ services/voice_session.py ──▶ VoiceRecvClient
  録音 ────┘        接続の所有と「占有」          （送信 + 受信）
```

- 接続の所有は `voice_session` に集約する。TTS も録音もここ経由で取りにくる
- 録音中は **hold** を立てる。TTS の「VC が空になったら切る」で接続ごと落と
  されないようにするため。占有中は別チャンネルへの移動もしない
- 音声の受信は discord.py 本体に無い（`play` はあるが受信 API が無い）。
  `discord-ext-voice-recv` の `VoiceRecvClient` を使い、入っていない環境では
  通常の `VoiceClient` に落ちる（読み上げは動き、録音だけが理由付きで断られる）
- ギルドごとの `asyncio.Lock` で接続の取得を直列化する。ロックの辞書は
  解放時に消さない（消すと、進行中の `acquire()` の最中に別の呼び出しが新しい
  ロックを作ってしまい排他が効かない）

### 7.2 読み上げ（TTS）

```
  メッセージ ──▶ 整形 ──▶ 辞書 ──▶ 合成(HTTP) ──▶ キュー ──▶ 再生
```

- 合成は外部の TTS サービス（`TTS_BASE_URL`）に HTTP で頼む。声の一覧も
  `/api/v1/voices` から取る
- 整形は URL・メンション・チャンネル参照・ロール・絵文字を読める語に置き換え、
  上限を超えたら「、以下省略」で切る
- 辞書は**1回の走査**で置き換える。1語ずつ `str.replace()` を重ねると前の
  規則の出力に次の規則が当たり、「鈴木→すずき」と「すずき→スズキ」を別々に
  登録しただけで「鈴木さん」が「スズキさん」になる（しかも結果が登録順に
  依存する）。同じ位置に複数当たるときは長い語を採る
- 再生はギルドごとの `asyncio.Queue` と再生ループ。声と速度はユーザーごとに
  上書きできる
- 一時的な VC 指定（`/tts join`）は temp override として持ち、設定より優先する

### 7.3 録音

受信できるのは「誰かが喋っているあいだのパケット」だけで、黙っているあいだは
何も来ない。素直に繋ぐと無音が詰まってトラック同士がずれるので、**録音開始
からの経過時間を基準に、足りない分を無音で埋めてから書く**。結果、全トラックが
同じ長さ・同じ時間軸に揃い、そのまま重ねて編集できる。

位置合わせは到着時刻ではなく RTP タイムスタンプ（48kHz 刻み）で行う。到着時刻で
置くと、ジッタのぶんだけ無音が挟まって時間軸が歪む。

PCM をそのまま置くと1人あたり毎時 690MB になるので、ユーザーごとに ffmpeg を
1つ立ち上げ、パイプへ流しながら mp3 にする。

**受信パケットを自分で組み立てる理由**: 拡張のジッタバッファは、順番待ちの穴が
空いた瞬間にバッファ全体を捨てて1つだけ返す。大量に落ちるうえ順不同で出てくる。
Opus は直前の状態を使って復号するので、順不同のまま入れると音が壊れる
（実測: 440Hz が 719Hz に化けた）。`_StreamAssembler` でもう一度並べ直してから
渡す。デコーダは **SSRC ごと**に持つ（user_id で持つと、同じ人が付け直した
SSRC が1つのデコーダに混ざる）。

**Opus のデコードも自前でやる**。ライブラリに任せると壊れたパケット1個で
`OpusError` が上がり、受信スレッドごと落ちて `stop_listening()` まで呼ばれる。
つまり壊れたパケット1個で録音が黙って止まる。

**RTP のパディングを剥がす**: voice_recv は剥がさない（`rtp.py` に「discord は
このビットを使っていないようだ」とあるが、実際には使われている）。帯域推定の
探査パケット（中身が全部パディング）が届き、Opus に渡すと「壊れている」と
言われる。本番では 247バイト全部 `0xF7` / 255バイト全部 `0xFF` として観測した。

**見張り**: 15秒ごとに、上限時間・VC の無人化・受信の停止・E2EE の割合を見る。
`on_voice_state_update` でも無人化は拾っているが、イベントを取り逃すと誰も
止める人がいなくなる。上限時間なしで録っているとそれが「永久に止まらない」に
なる。

### 7.4 E2EE（DAVE）

Discord は 2024年9月から音声を端から端まで暗号化していて、2026年3月2日から
ボットにも必須（未対応だと音声接続がクローズコード 4017 で拒否される）。

鍵交換（MLS）は discord.py 2.7.1 が実装済みで `davey` が入っていれば自動で
成立するが、**discord.py が使うのは送信側だけ**で受信側の復号はどこにも無い
（discord-ext-voice-recv にも無い）。そこを `services/dave.py` が補う。

フレームの見分け方は末尾のマーカー（`0xFAFA`）と補助データ長。偶然 `0xFAFA` が
並んだ平文を誤判定しないよう補助データ長まで確認し、RTP パディングが残って
いる場合に備えて末尾から少しさかのぼって探す。

暗号文をそのまま Opus に渡すと、例外にならず**雑音が返る**。「録れているのに
聞けない」が一番たちの悪い壊れ方なので、復号できないフレームは音として書かず
数えるだけにし、割合が高ければ理由を添えて停止する。

### 7.5 書き出しと自動確認

停止時に、各トラックを閉じてから ZIP にまとめる。中身は各トラックの mp3、
ミキサー用の索引（`mixer.json`）、`info.json`、`info.txt`。

**書き出した音が声として成立しているかを測る**。長さもトラック数も正しいのに
中身が雑音、という壊れ方を実際にした。指標は周期性（自己相関の山の高さ）で、
声は準周期的なので山が立ち、雑音では立たない（実測: 正常 0.51 / 白色雑音
0.17）。スペクトル平坦度も試したが mp3 のローパスに支配されて区別できなかった。
下回ったトラックは Discord の結果とミキサーの両方に印を付ける。

配信は `djaudio_cache` に登録してトークンを発行し、保存期間（既定7日）が
過ぎたら消える。

### 7.6 ミキサー（管理画面）

数時間 × 人数ぶんを `decodeAudioData` で丸ごと展開するとメモリが破綻する
（6時間×8人で 63GB）。ZIP 内の mp3 は**無圧縮**（`ZIP_STORED`）で格納し、
展開せずに「その位置から何バイト」で直接読めるようにしてある。

再生の経路は2つある。

**区切り配信（既定）**

全トラックの同じ区間を「1トラック＝1チャンネル」の生 PCM にまとめて渡し、
`ChannelSplitter` で分ける。

```
  区切り(PCM) → AudioBufferSource → ChannelSplitter
      → ch0 → Gain(フェーダー) → Panner → Analyser → マスター
      → ch1 → …
```

**音源が1つなので時計も1つしかない。トラック同士がずれようがない。**
先の区間を 12 秒ぶん先読みし、`AudioContext` の時計の上に並べる。

設計上の判断はどれも実測から決めた。

- **コンテナに入れない**。Opus(WebM) は再生できるがブラウザ側でチャンネル順が
  入れ替わる（ffmpeg で読み直すと正しい順なので、並べ替えているのは復号側）。
  WAV は 8ch では順序も保たれたが、3ch だと
  `EncodingError: Unable to decode audio data` で落ちた（ffmpeg が
  `channelMask=0xb` = FL/FR/LFE の 2.1 を書くため）。生の PCM なら並びは
  書いた順そのもので、復号器の解釈が入らない
- **ZIP から直接読む**。ffmpeg の `subfile` プロトコルで無圧縮メンバーの
  範囲だけを読ませるので、トラックを取り出して置いておく必要がない
- **位置合わせは「粗く入力側で飛んでから、出力側で正確に切る」**。入力側の
  `-ss` だけだと区切りの先頭に無音が入る（subfile 越しの mp3 は索引を使った
  正確なシークができない）。実測では要求位置によって 110〜195ms とばらつき、
  継ぎ目ごとに音が欠けたうえ欠ける量も一定しなかった
- **1トラック＝モノラル**。Discord の音声はもともとモノラルで、録音時に
  ステレオへ複製されているだけなので情報は失われない。帯域も半分になる

**従来経路（古いアーカイブ・33人以上）**

圧縮されたまま入っている古いアーカイブと、`ChannelSplitter` の上限（32）を
超える人数では、トラックごとに `<audio>` を持つ。このとき時計が人数ぶん並ぶので
補正が要る。

- 頭出しと再生の前に、全トラックのメタデータが読めるまで待つ。読めていない
  `<audio>` は `currentTime` への代入を**黙って捨てる**ので、待たずに鳴らすと
  そのトラックだけ 0 秒から始まる
- 同期の基準は最初の並びに固定する。`tracks[0]` を基準にすると、並べ替えた
  だけで基準が別のトラックの時計へ入れ替わる
- 小さなずれは再生速度で吸収し（±6%、音程は保つ）、頭出しのやり直しは
  0.75 秒を超えたときだけ。頭出しは音が途切れるので、細かいずれのたびに
  やると鳴り直しになる

**波形**は表示している範囲だけ描く。6時間を 40px/秒 で並べると 86万px になり、
キャンバスの幅の上限（32767px 前後）を超えるため。目盛りは上限 3000 点まで
間引くが、**間引き幅は全トラックで1つに揃え、間引いたあとの「1点＝何秒か」を
索引に書く**。ここを揃えないと、長い録音で波形が時間軸の先頭に潰れ、長さの
違うトラック同士でも縮尺が食い違う。

区間の書き出しは、無圧縮で入っている mp3 をフレーム境界で切るだけ（`-c copy`）。
再エンコードしないので速く、音も劣化せず、切り出しても時間軸は揃ったまま。

## 8. 音源の取り込みと配信（DJAudio）

```
  設定チャンネルへ URL 投稿
        │
        ▼
  djaudio_site_detection      yt-dlp の info.json から媒体を判定
        │
        ▼
  yt-dlp + ffmpeg             mp3 に変換
        │
        ▼
  djaudio_isrc_meta           Deezer の公開 API でメタデータを補完
        │                     （ISRC があれば完全一致、無ければ媒体別クエリ）
        ▼
  djaudio_cache.register_file トークン発行、guild_id と TTL を紐づけ
        │
        ▼
  /dlaudio/files/<guild_id>/<token>
```

配信ルータ（`services/djaudio_cdn.py`）は `webapp_admin` にも `cdn_main` にも
依存せず、どちらからでも import できる。

アクセス制御はトークン（uuid4）と guild_id の照合。期限切れは 410、別ギルドは
403、そもそも無いものは 404 を返す。TTL を過ぎたファイルは定期的に消す。

録音のアーカイブも同じ仕組みに載る（`kind="recording"`）。ミキサー向けに
索引（`/mixer`）・トラック単体（`/stem/{index}`、Range 対応）・区間の
切り出し（`/clip`）が生えている。

ffmpeg を使う処理（切り出し・区切り配信）は**必ず `asyncio.to_thread` へ
逃がす**。直接 await すると、そのワーカーが受けている他のリクエストまで
巻き添えで止まる（実測: 7秒かかる処理のあいだ、ヘルスチェックが3.96秒
待たされた）。

## 9. セキュリティ機能

### 9.1 メッセージの検査

```
  on_message
     │
     ├─ Bot / DM なら何もしない
     ├─ ChatGPT 応答チャンネルで、リンクも添付も無いなら検査しない
     │
     ├─ バイパス判定（信頼ユーザー / 免除ロール）
     │     ├─ bypassed      → ログだけ残して通す
     │     └─ check_failed  → 判定できなかった。何もしない（後述）
     │
     ├─ スパム判定（15秒窓で4回以上）        → SUSPICIOUS
     ├─ VirusTotal（URL / 添付ファイル）      → 悪性なら DANGEROUS
     ├─ LLM 判定（gpt_assess）                → DANGEROUS / SUSPICIOUS / SAFE
     └─ 新規参加者（7日以内）なら判定を厳しめに
```

判定の材料は積み上げ式で、最終判断は LLM に委ねる。VirusTotal で悪性判定が
出た時点で LLM を待たずに危険と決める（`MALICIOUS_THRESHOLD`）。

進捗は逐次メッセージを更新して見せる（検査に時間がかかるため）。

### 9.2 バイパス判定を3状態にする理由

```python
class BypassResult(NamedTuple):
    bypassed: bool
    reason: str = ""
    check_failed: bool = False
```

「判定できなかった」を「バイパスなし」と同じ扱いにすると、設定を読めなかった
だけで全ロール剥奪（元に戻せない）まで進んでしまう。3つの状態を区別する。

### 9.3 スパム / レイド検出

どちらもプロセス内のメモリだけで動く簡単なもの。

- **スパム**: `(guild_id, user_id)` ごとに直近15秒の投稿時刻を持ち、4件以上で
  スパム。最短間隔も返して LLM の材料にする
- **VCレイド**: チャンネルごとに直近20秒の入室を持ち、**表示名の先頭4文字が
  同じ**ものが5件集まったらレイド

どちらも辞書が増え続けないよう、一定回数ごとに期限切れを間引く。

### 9.4 URL の検査

外から取ってきた URL は `services/url_safety.py` の
`validate_public_http_url()` を通す。内部ネットワーク（プライベートアドレス、
ループバック、リンクローカル）へのリクエストを踏ませないため。ニュースの
フィード URL、Web App の Push エンドポイントなど、利用者が指定できる URL は
すべてここを通る。

## 10. ユーザー状態監査

「いま在籍しているか」と「いつ何があったか」を長期に残す。Discord の監査ログは
保持期間が限られていて、退出した人の履歴も追えないため。

```
  user_state_current   ユーザーごとに1行。現在の状態・ロール・権限・最終更新
  user_state_event     出来事ごとに1行。参加 / 退出 / BAN / KICK / ロール変化
```

- **イベント記録**: `on_member_join` などから `record_user_state_event()` を
  呼ぶ。BAN / KICK は Discord の監査ログを引いて実行者を特定する（取れないこと
  もあるので、数回リトライしてから諦める）
- **同期**: 起動時に全ギルドのメンバーと BAN 一覧を取り、現在の状態を合わせる。
  `fetch_members` が権限で失敗したらキャッシュに落ちる
- **整合性修復**: 30分ごとに `repair_user_state_integrity()` が、イベントの
  履歴と現在の状態の食い違いを直す。既定では修復時にイベントを書かない
  （`USER_STATE_AUTO_REPAIR_WRITE_EVENTS`）
- **保持期間**: 既定3650日（10年）。`USER_STATE_RETENTION_DAYS` は
  **伸ばす方向にしか受け付けない**（`minimum=3650`）。誤って短い値を入れた
  だけで監査履歴が消える事故を防ぐため

DB エラーは「直せるもの」（`OperationalError` / `ProgrammingError`）だけを
選んで、テーブルの作り直しを1回試す。

## 11. 通知系の機能

### 11.1 地震アラート

P2PQuake の WebSocket に常時つながり、届いたイベントをギルドごとの設定
（通知チャンネル、最小震度、通知種別）に従って配る。

| コード | 種別 |
|---|---|
| 551 | 地震情報（確定） |
| 552 | 津波情報 |
| 554 | 緊急地震速報（警報） |
| 556 | 緊急地震速報（予報） |

`services/earthquake_service.py` は1,300行と大きいが、内訳は表示のための
描画処理が中心（震度バッジの画像生成、震央地図の生成、フォントの読み込み、
Embed の組み立て、JMA の詳細ページへのリンク）。同じイベントを二度送らない
よう ID で重複を弾き、その集合は期限つきキャッシュで増え続けないようにする。

開発者パネルから過去のイベントをリプレイできる（`eq_replay`）。送信先を
明示指定すれば、地震アラートの設定を持たないギルドでも確認できる。

#### 震度分布の画像

一目で読めることを最優先にしてある。

- **観測点は「角丸＋震度の数字」の札**。色だけの丸にしていたころは、震度4(黄)
  と5弱(橙)が色相で隣り合うため、Discord に縮小されて届くと見分けられなかった。
  凡例と同じ形・同じ読み方に揃えてある。
- **札の大きさは震度で変える**（震度1で18px、6弱以上で34px）。色が読めなくても
  視線が強い方へ落ちる。
- **揺れた県は面でも塗る**。点だけでは「県のどこか1点が揺れた」ようにしか
  見えず、震央からどちらへ強く伝わったのかが分からない。
- **重なったら弱い方を落とす**。ただし最大震度の札は無条件で置く。見出しに
  出す震度が地図に無いと、画像と本文が食い違って見える。
- **震源印は札より先に描く**（札の下）。輪と十字なので札の外へはみ出して
  見える。震央と県庁所在地がほぼ同じ場所の内陸地震で、震源印が最大震度の札を
  覆って数字が読めなくなるのを避ける。
- **最大震度の札は地図の中に持たない**。埋め込みには最大震度だけの画像が
  サムネイルとして付く（`_generate_badge`）ので、地図の右上にも置くと同じ札が
  ひとつの吹き出しに2つ出る。地図側は見出しの文字列（「最大震度 4」）で足りる。

県の輪郭は `assets/jp_prefectures.json`。**地球地図日本 第2.1版 行政界
（国土地理院）**を `tools/build_pref_polygons.py` で加工したもので、市区町村
ポリゴン 2914 件を都道府県ごとに束ね、0.004度（約400m）で間引いてある。
同じ県を同じ色で塗るため県の内側に境界線は出ず、図形を融合する計算をせずに
済ませている。差分の整数列で持たせて 1.2MB → 395KB。

利用条件は**公共データ利用規約（PDL1.0）**で、出典の記載と、加工した旨の
記載が条件（画像の左下に入れている）。

### 11.2 ニュース

Google ニュースの RSS をギルドごとに購読し、5分ごとに新着を配る。既読は
フィードごとに URL のハッシュで持ち、**保存側で直近100件に切る**
（`settings.json` が際限なく膨らまないよう、切るのは書く側の責任にしてある）。
要約は Groq に頼み、失敗したら要約なしで送る。ファビコンは配信元のドメインから
引く。

### 11.3 スティッキーメッセージ

チャンネルの一番下に固定したいメッセージ。新しい投稿が来たら、古いスティッキーを
消して貼り直す。チャンネルごとに `asyncio.Lock` を持ち、連投で二重に貼らない
ようにする。削除に失敗したぶんは「保留」として記録し、30秒ごとの定期タスクが
片付ける。

### 11.4 ウェルカム / グッバイ、VC通知、リアクションロール

- **ウェルカム / グッバイ**: テンプレートに `{user}` `{username}` `{server}`
  `{count}` を埋める。既定の文面はコードに持つ（管理画面のプレビューと Bot が
  同じ関数を使う）
- **VC通知**: 誰かが VC に入ったら知らせる。ロールメンションを付けられるが、
  連投を防ぐためギルドごとに最後に送った時刻を覚えておく
- **リアクションロール**: 保存構造は `message_id → {emoji: role_id}` の入れ子。
  一覧では `"<message_id>:<emoji>"` を項目IDとして平坦化して扱う

### 11.5 ログ

`services/logging_service.py` が、ギルドごとのログチャンネルとレベル
（`NONE` / `ERROR` / `INFO` / `DEBUG`）を持ち、`log_action()` で Embed を送る。
どのイベントをどのレベルで出すかは呼び出し側が決める。

## 12. 貴金属トラッカー

Discord を知らない独立した Web アプリ。金・銀・プラチナの円/g を追い、
7日先の予測レンジを出し、PWA として通知も送る。

### 12.1 データの流れ

```
  MetalpriceAPI ──▶ snapshot_service ──▶ metal_price_daily
                                              │
                            ┌─────────────────┼─────────────────┐
                            ▼                 ▼                 ▼
                     forecast_series    forecast_signals   repair_service
                     （欠損に強い       （為替・ニュース・  （欠損の穴埋め）
                       リターン系列）      LLM のシグナル）
                            │                 │
                            └────────┬────────┘
                                     ▼
                             forecast_models
                             （予測区間の組み立て）
                                     │
                                     ▼
                     weekly_forecast_meta / _daily
                                     │
                                     ▼
                          forecast_accuracy_log（答え合わせ）
```

定期ジョブ（APScheduler、JST）:

| ジョブ | いつ |
|---|---|
| 日次スナップショット + 予測 | 00:00 |
| 予測の再計算 | 6 / 12 / 18時（`FORECAST_REFRESH_EXTRA_HOURS_JST`） |
| Push 通知（変動の大きい金属） | `PUSH_NOTIFY_HOUR_JST` |
| データ整合性の自動修復 | 30分間隔 |

### 12.2 なぜ点予測をやめたか

本番の実データでウォークフォワード検証したところ、旧 SARIMAX モデルは
「7日後も今日と同じ価格」と言うだけのランダムウォークより**明確に劣っていた**。

```
    平均絶対誤差      モデル 5.51%  /  naive 3.37%  /  trend 3.94%
    方向的中率        モデル 40.6%（コイン投げ以下）
    naive に勝った割合 18.6%
```

さらに102回中102回すべてマイナス予測で、実質「標本期間内のドリフトの外挿」で
しかなかった。ドリフト減衰係数λを較正すると **λ=0（＝現在価格をそのまま中心に
する）が最良**で、λを上げるほど単調に悪化した。

そこで点予測をやめ、**「現在価格を中心とし、過去の値動きから求めた区間で幅を
示す」**モデル（`interval_rw_v1`）に置き換えた。外部シグナル（為替・ニュース・
AI判定）は履歴を再現できず有効性が未検証なので、中心をわずかに傾ける tilt と
してのみ残し、`FORECAST_TILT_MAX_PCT_PER_DAY`（既定 0.15%/日 = 7日で約±1.05%）で
厳しく制限している。

### 12.3 欠損に強い系列を作る

本番データには収集ジョブの停止による毎月10〜11日の欠損があり、その多日ぶんの
変動が「1日分のリターン」として扱われていた。通常±1%の系列に6〜10倍の外れ値が
混入し、ボラティリティを実測で約2倍（silver 1.50% → 3.07%/日）に見せていた。
`forecast_series.py` が経過日数を考慮した系列を組み立てる。

### 12.4 常時、自分を測る

区間予測にとって被覆率は最も本質的な品質指標で（名目80%なら実測も80%であるべき）、
これが無いと精度を評価できない。そこで予測のたびに、

- 予測値と区間の上下限
- **傾きを掛けない予測（＝予測時点の現在価格）**

を一緒に記録し、7日後に実勢価格と突き合わせる（`forecast_accuracy_log`）。
2つ目があることで、「外部シグナルによる傾きが本当に予測を良くしているか」と
「予測が何もしないより良いか」を本番で常時測れる。

モデルを変えたら `tools/backtest_forecast.py` を通す。合格基準は
**MAE が naive を上回らないこと**と**名目80%区間の実測被覆率が70〜90%に
収まること**。

### 12.5 PWA と Push

- **キャッシュバスティング**: `index.html` の `?v=` と `sw.js` の
  `CACHE_NAME` を手で更新する運用だと、忘れたときに「コードは新しいのに配信は
  古いまま」になる（実際に一度起きた）。`asset_version.py` が配信時にファイル
  内容のハッシュを埋め込み、中身が変われば必ず URL とキャッシュ名も変わる状態を
  機械的に保証する。ハッシュ計算は mtime/size が変わったときだけ行う
- **Web Push**: VAPID の鍵は `VAPID_KEYS_DIR` に置くか環境変数で渡す。無ければ
  生成する。購読エンドポイントは `PUSH_ALLOWED_ENDPOINT_SUFFIXES` で絞れる。
  送信に失敗した購読（410 など）は消す
- **重複送信の防止**: `notification_dispatch` に送信記録を残す

### 12.6 公開面の守り

`webapp/security.py` に、

- **`SecurityHeadersMiddleware`**: CSP、`X-Frame-Options: DENY`、HSTS、
  `Referrer-Policy: no-referrer`、COOP / CORP、`frame-ancestors 'none'` など
- **`RateLimitMiddleware`**: IP ごとの制限。プロキシ配下の実 IP は
  `TRUSTED_PROXY_CIDRS` に載っている相手からの `X-Forwarded-For` だけ信じる
- **`TrustedHostMiddleware`**: `ALLOWED_HOSTS`
- **GZip**

## 14. 全体を貫く約束

コードの中で繰り返し守っている規則。新しく足すときもここに合わせる。

### 同じ判定を2箇所に書かない

片方だけ直して取りこぼす、が実際に何度も起きた。判定は1つの関数に寄せ、
関連する2つの問い（「開発者パネルは存在するか」と「この人は開発者か」など）が
別々の読み方をしている状態を作らない。

### 設定は読む側まで通す

保存できて画面にも出るのに、送る側が一度も読んでいない、という設定が実際に
あった（録音の通知チャンネル）。設定を足したら、それを**使う**場所まで
繋がっていることを確かめる。`tools/check_admin_schema.py` が get/set の往復を
機械的に確かめる。

### 黙って何もしない分岐を作らない

条件に当たらなかったとき、ファイルだけ消えて「受信」「完了」のログが残り、
何も実行されないまま成功に見える、という状態を避ける。理由を1つに特定して
ログへ残す。

例外を握りつぶすときも、必ず理由を残す。「握りつぶしてよい」と判断した根拠を
コメントに書く。

### 既定は安全側・不明は出さない・不都合も隠さない

- 自動録音の既定はオフ。録音の開始告知は**無効化できない**
- 書き出した録音が雑音になっていないかを測り、疑わしければ Discord の結果と
  ミキサーの両方に印を付ける。落として聞くまで気づけないのでは遅い
- ロールの判定に失敗したときは「バイパスなし」ではなく「判定できなかった」を
  返す。同じ扱いにすると、設定を読めなかっただけで全ロール剥奪まで進む
- 監査履歴の保持期間は伸ばす方向にしか変えられない
- 予測は「何もしないより良いか」を本番で常時測る

### 環境変数は envutil を通す

`int(os.environ.get("X", "600"))` は、`X=`（空文字で宣言だけ）や壊れた値で
**インポート時に落ちる**。`Path(os.getenv("SETTINGS_DIR", 既定値))` は空文字だと
`Path("")` = カレントディレクトリになり、書く側と読む側で場所がずれる。
`envutil` の関数はいずれも例外を投げず、理由をログに残して既定値へ倒す。
範囲のクランプもログに残す（黙って値が変わらないように）。

### イベントループを塞がない

FastAPI のハンドラから重い同期処理（ffmpeg、長い計算）を直接呼ぶと、その
ワーカーが受けている**他のリクエストまで巻き添えで止まる**。`asyncio.to_thread`
へ逃がす。

### 数値の桁を落とさない

Discord の ID は19桁で、JavaScript の数値では正確に扱えない。JSON へ入れる
ときは文字列にする（→ 6.3）。

### 表示のための処理はサーバでやる

一覧の絞り込み・ページ送り・ラベル化・JST 整形はサーバ側に置き、クライアントは
受け取った文字列を並べるだけにする。件数が増えるほど重くなる形を作らない。

## 15. 検証

DB も Discord も要らない範囲で、機械的に確かめられるものは全部確かめる。

```bash
python -m unittest discover -s tests -t .     # 380 件。Discord/ネットワークに触らない
python tools/check_admin_schema.py            # スキーマと services の噛み合わせ
python tools/check_admin_ui.py                # 管理画面を実ブラウザで操作
python tools/check_recording_mixer.py         # 波形の縮尺と再生位置を実ブラウザで
python tools/check_recording_audio.py         # 録音が声として成立しているか
python tools/backtest_forecast.py             # 予測モデルのウォークフォワード検証
python tools/generate_admin_docs.py --check   # ドキュメントがスキーマと一致するか
python tools/check_requirements.py            # 依存の固定が Docker と同じ条件で解けるか
```

いずれも一時ディレクトリを `SETTINGS_DIR` にして動くので、本物の
`settings.json` は変更しない。`pytest` は入っていないので `unittest` を使う。

`check_requirements.py` があるのは、固定した版を「手元の環境に入っているもの」
から取ってくると壊れたピンを書いてしまうため。実際 `PyNaCl==1.6.2` を固定して
`discord.py[voice]` の `PyNaCl<1.6` と衝突し、docker build が落ちた。

### テストの書き方の方針

- **「同じことがまた起きたら落ちる」形で書く**。直したバグには、その症状を
  再現するテストを足す
- 直した内容を外したコピーで、実際にそのテストが落ちることを確かめる。
  落ちないテストは何も守っていない
- ブラウザの中でしか起きないこと（描画、`<audio>` の挙動）は playwright で
  実ブラウザに確かめさせる。ただし**再現できないものは「できない」と書く**。
  たとえば headless Chromium では `<audio>` 同士がほとんど離れないため、
  再生位置のずれは検査で再現できていない
- テストの docstring に「なぜこれを守るのか」を書く。何を確かめているかは
  コードを読めば分かるが、なぜ大事かは書かないと残らない

## 16. 分かっている限界

| こと | 内容 |
|---|---|
| シグナルの遅延 | 管理画面からの操作が Bot に届くまで最大30秒 |
| 管理画面の複数ワーカー | メトリクス・監視・レート制限がプロセスローカル。`ADMIN_WORKERS>1` では表示値がズレる（起動時に警告する）。レート制限を共有するには Redis が要る |
| settings.json の書き込み | ロックはポーリングで、競合すると最大10秒待つ。待ちはスレッドへ逃がしてある（[5.1](#51-非同期から設定を書くときは必ずスレッドへ逃がす)）ので呼び出し側のイベントループは止まらないが、書き込みが稀であることは前提のまま |
| スパム / レイド検出 | プロセス内のメモリだけで動く。Bot を再起動すると履歴が消え、複数インスタンスでは共有されない |
| ミキサーの拡大率の下限 | 1px/秒 が下限なので、長い録音は「全体」でも画面に収まらない。横スクロールで見る |
| 区切り配信の帯域 | 生の PCM を送るので、8人なら再生中ずっと約 6 Mbps 使う（1秒あたり 8ch × 48kHz × 2バイト）。同一ホストや LAN の管理画面を前提にしている |
| 区切り配信の CPU | 6秒ごとに ffmpeg を1回起動する。人数ぶんの入力を1回でまとめるので起動回数は再生時間に比例するが、視聴者数には比例して増える |
| 波形の粒度 | 上限 3000 点。6時間なら1点あたり約7秒で、拡大してもそれ以上細かくならない |
| 録音と E2EE | `davey` が入っていない環境では録音できない（理由を添えて断る） |
| 予測 | 時系列外挿に予測力が無いことは実証済み。外部シグナルの有効性は未検証で、中心の傾きを厳しく制限したうえで本番で測り続けている段階 |
| 予測の材料の欠損 | 収集ジョブが止まると履歴に穴が空く。系列側で吸収しているが、穴が大きいほど区間は広がる |
| 監査ログからの実行者特定 | BAN / KICK の実行者は Discord の監査ログを引いて特定する。権限が無い、または反映が遅れると取れない |
