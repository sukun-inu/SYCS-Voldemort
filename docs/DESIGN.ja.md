## 1. 全体の形

3つのプロセスが1つのデータディレクトリと2つのデータベースを共有する。

```
                    ┌──────────────────────────────┐
   Discord  ───────▶│  Bot            main.py      │
                    │  イベント / スラッシュコマンド │
                    └───────┬──────────────┬───────┘
                            │              │
            ┌───────────────┴──┐        ┌──┴──────────────────┐
            │  /app/data       │        │  Postgres           │
            │  settings.json   │        │  metal_prices       │
            │  _dev_signals/   │        │  user_state_audit   │
            │  djaudio_cache/  │        └──┬──────────────────┘
            │  logs/           │           │
            └───────────────┬──┘           │
                            │              │
   ブラウザ ───────▶┌───────┴──────────────┴───────┐
                    │  Admin UI    admin_main.py    │  :5001
                    │  設定 / 監視 / SQL / ミキサー  │
                    │  + /dlaudio（配信）           │
                    └──────────────────────────────┘

   ブラウザ ───────▶┌──────────────────────────────┐
                    │  Web App     web_main.py     │  :8000
                    │  貴金属トラッカー（PWA）      │
                    └──────────────────────────────┘
```

| プロセス | 入口 | 役割 |
|---|---|---|
| Bot | `main.py` → `bot_setup.py` | Discord のイベント処理、スラッシュコマンド、定期タスク |
| Admin UI | `admin_main.py` → `webapp_admin/app.py` | 設定画面、監視、SQL エディタ、録音ミキサー、`/dlaudio` の配信 |
| Web App | `web_main.py` → `webapp/app.py` | 貴金属価格トラッカー（公開 PWA）、週次予測 |
| CDN（任意） | `cdn_main.py` | `/dlaudio` だけを別プロセスで受け持つ。管理画面と同じルータを載せる |

`docker-compose.yml` で立つのは上の3つ（＋ Postgres と初期化ジョブ）。
`cdn_main.py` は配信を分離したいときの選択肢で、既定の構成では管理画面が
`/dlaudio` を持つ。

### なぜプロセスを分けるか

Bot は Discord のゲートウェイに常時つながっていて、落とすと再接続に時間が
かかる。管理画面の再起動や重いクエリで Bot を巻き込みたくない。逆に、
Discord へ送る・VC へ繋ぐといった操作は Bot にしかできない。そこで
**「状態は共有し、操作はシグナルで頼む」**形にしている（→ 3節）。

## 2. 状態をどこに置くか

| 置き場 | 中身 | 読み書きする側 |
|---|---|---|
| `data/settings.json` | ギルドごとの全設定 | Bot / Admin（`services/settings_store.py` 経由） |
| `data/_dev_signals/` | Bot への依頼（→ 3節） | Admin が書き、Bot が読む |
| `data/djaudio_cache/` | 配信するファイルとそのメタ | Bot が書き、`/dlaudio` が読む |
| `data/logs/` | 各プロセスのログ | それぞれ |
| `data/_recording_state.json` | 録音中の状況 | Bot が書き、Admin が読む |
| Postgres `metal_prices` | 価格の履歴、予測、購読 | Web App |
| Postgres `user_state_audit` | 参加/退出・BAN・ロール変化の記録 | Bot / Admin |

`data/` は Docker のボリューム `app_data` として3つのコンテナすべてに
`/app/data` でマウントされる。場所の解決は必ず `SETTINGS_DIR` を通す。

### settings.json をデータベースに置かない理由

設定は「ギルドごとの入れ子の辞書」で、更新は人の操作の速さでしか起きない。
それに対して読み出しはメッセージのたびに走る。ファイル＋メモリキャッシュ
（ファイル署名 mtime_ns + size が変わったら自動で捨てる）にしておくと、
別プロセスからの更新も検知できて、DB を1つ増やさずに済む。

書き込みはロックファイルで直列化する（`_settings_file_lock`）。ロックが
残ったまま死んだ場合に備えて、一定時間を過ぎたロックは奪える。

### 設定の読み書きは1本の関数を通す

管理画面のスキーマ（`webapp_admin/schema/`）は `settings.json` の構造を
**知らない**。値の出し入れは `Field.get` / `Field.set` が指す
`services/*` の関数に委ねる。Bot 側も同じ関数を読むので、管理画面と Bot で
設定の解釈がズレない。

これは実際に何度も踏んだ問題への対処で、`tools/check_admin_schema.py` が
「スキーマの各項目に get/set があり、それが実在して噛み合っているか」を
機械的に確かめる。

## 3. Bot への依頼（シグナル）

管理画面から「録音を開始」「通知をテスト送信」を押したとき、その処理は
Bot にしかできない。共有ディレクトリにファイルを1つ置き、Bot が30秒ごとに
拾って実行する。実装は `services/dev_signals.py` に集約してある。

```
Admin  ──▶  data/_dev_signals/recording_start.<一意>.signal  ──▶  Bot
                        （payload に guild_id / channel_id）
```

ファイル名の付け方に意味がある。

| 形 | 用途 | 例 |
|---|---|---|
| `<用途>.signal` | 何度実行しても結果が同じもの。溜める意味が無いので上書き | `news_feeds` |
| `<用途>.<一意>.signal` | 対象が payload の中にしかないもの。上書きすると別の対象宛が消える | `recording_start`, `eq_replay`, `test_*` |

後者を用途名だけで書いていたときは、2つのサーバーの管理者が30秒以内に
操作すると先の1件が黙って消えていた。押した側には「キューに追加しました」と
出たままで、ログにも残らない。Bot 側は「最初の `.` まで」を用途名として
読むので、どちらの形も同じ分岐に落ちる。

**制約**: 反映まで最大30秒かかる。押した瞬間に結果は返らないので、UI は
「キューに追加しました」と伝えて状況を数秒おきに取り直す。即時性が要る
操作をここに載せてはいけない。

## 4. 管理画面

### スキーマ駆動

「管理UIにどんな設定が存在するか」の単一の情報源は
`webapp_admin/schema/panels/*.py` の宣言。ここから、

- フォームの描画（クライアント）
- 入力値の検証（サーバ）
- API の受け口
- スタートメニューのタイル
- `docs/ADMIN.ja.md` の設定表（`tools/generate_admin_docs.py` が生成）

がすべて派生する。個別に定義しない。設定を1つ増やすときに触るのは宣言と
`services/*` の get/set だけで、画面・検証・ドキュメントは付いてくる。

スキーマから描けない画面（監視、SQL エディタ、VC録音など）は
`schema/panels/custom.py` に「タイルとしての情報」だけを置き、中身は
`static/js/apps/*.js` が専用の API を読んで描く。並び順を1箇所で管理する
ため、これらも同じ登録簿に載せる。

### デスクトップ風のシェル

画面はデスクトップに見立てた1枚で、設定はその上のウィンドウとして開く。
位置と開いていたアプリはブラウザに保存して復元する。

- 設定の変更は**明示保存**（保存ボタンを押すまで反映しない）
- 一覧への**追加・削除は即時**（保存ボタンには含めない）

この2つを混ぜないのは、一覧の操作を保存待ちにすると「追加したのに消える」
事故が起きるため。

### 開発者専用の面

`DEV_USER_ID` に一致するユーザーだけが開発者パネルと SQL エディタを開ける。
**未設定なら 404**（存在しないものとして扱う）。「設定されているか」の判定は
`webapp_admin/security.dev_user_id()` に一本化してある。

SQL エディタの安全側の既定:

- 読み取り専用トランザクション。**SQL の文字列判定ではなく** Postgres 側で
  `READ ONLY` を宣言するので抜け道が無い
- 接続先はアプリ自身が持つ DSN のみ。画面から変えられるのは「同じサーバ上の
  データベース名」だけで、ホストや資格情報は差し替えられない
- `statement_timeout` を設定し、行はサーバ側カーソルで上限まで
- 接続はリクエストごとに開いて閉じる（アプリ本体のプールとは別なので、
  重いクエリで Bot や管理画面を止めない）

## 5. 音声まわり

Discord の bot は1ギルドにつき音声接続を**1本**しか持てない。読み上げ（送信）と
録音（受信）を同時に使うには、同じ `VoiceClient` を共有するしかない。

```
  TTS ─────┐
           ├──▶ services/voice_session.py ──▶ VoiceRecvClient
  録音 ────┘        接続の所有と「占有」          （送信 + 受信）
```

- 接続の所有は `voice_session` に集約する。TTS も録音もここ経由で取りにくる
- 録音中は **hold** を立てる。TTS の「VC が空になったら切る」で接続ごと
  落とされないようにするため。占有中は別チャンネルへの移動もしない
- 音声の受信は discord.py 本体に無い（`play` はあるが受信 API が無い）。
  `discord-ext-voice-recv` の `VoiceRecvClient` を使い、入っていない環境では
  通常の `VoiceClient` に落ちる（読み上げは動き、録音だけが理由付きで断られる）

### 録音のトラック

受信できるのは「誰かが喋っているあいだのパケット」だけで、黙っているあいだは
何も来ない。素直に繋ぐと無音が詰まってトラック同士がずれるので、**録音開始からの
経過時間を基準に、足りない分を無音で埋めてから書く**。結果、全トラックが同じ
長さ・同じ時間軸に揃い、そのまま重ねて編集できる。

位置合わせは到着時刻ではなく RTP タイムスタンプ（48kHz 刻み）で行う。到着時刻で
置くと、ジッタのぶんだけ無音が挟まって時間軸が歪む。

PCM をそのまま置くと1人あたり毎時 690MB になるので、ユーザーごとに ffmpeg を
1つ立ち上げ、パイプへ流しながら mp3 にする。

### 受信パケットを自分で組み立てる理由

拡張のジッタバッファは、順番待ちの穴が空いた瞬間にバッファ全体を捨てて1つだけ
返す。大量に落ちるうえ順不同で出てくる。Opus は直前の状態を使って復号するので、
順不同のまま入れると音が壊れる（実測: 440Hz が 719Hz に化けた）。そこで
`_StreamAssembler` でもう一度並べ直してから渡す。デコーダは SSRC ごとに持つ。

Opus のデコードも自前でやる。ライブラリに任せると壊れたパケット1個で
`OpusError` が上がり、受信スレッドごと落ちて録音が黙って止まる。

### E2EE（DAVE）

Discord は音声を端から端まで暗号化していて、2026年3月2日からボットにも必須。
鍵交換（MLS）は discord.py が実装済みだが、**使うのは送信側だけ**で受信側の
復号はどこにも無い。そこを `services/dave.py` が補う。

暗号文をそのまま Opus に渡すと、例外にならず**雑音が返る**。「録れているのに
聞けない」が一番たちの悪い壊れ方なので、復号できないフレームは音として書かず
数えるだけにし、割合が高ければ理由を添えて停止する。

### ミキサー（管理画面）

数時間 × 人数ぶんを `decodeAudioData` で展開するとメモリが破綻する。そこで
`<audio>` のストリーミング再生に Web Audio を挟む。

```
  <audio> → Gain(フェーダー) → StereoPanner → Analyser(メーター)
          → マスター Gain → マスター Analyser → 出力
```

ZIP 内の mp3 は**無圧縮**（`ZIP_STORED`）で格納する。展開せずに「その位置から
何バイト」で直接読めるので、Range リクエストでの頭出しが素直に通る。

同期には注意が要る。`<audio>` は1本ずつ別の時計で動く。

- 頭出しと再生の前に、全トラックのメタデータが読めるまで待つ。読めていない
  `<audio>` は `currentTime` への代入を**黙って捨てる**ので、待たずに鳴らすと
  そのトラックだけ 0 秒から始まる
- 同期の基準は最初の並びに固定する。`tracks[0]` を基準にすると、並べ替えた
  だけで基準が別のトラックの時計へ入れ替わる
- 小さなずれは再生速度で吸収し（±6%、音程は保つ）、頭出しのやり直しは
  0.75 秒を超えたときだけ。頭出しは音が途切れるので、細かいずれのたびに
  やると鳴り直しになる

波形は**表示している範囲だけ**描く。6時間を 40px/秒 で並べると 86万px になり、
キャンバスの幅の上限（32767px 前後）を超えるため。目盛りは上限 3000 点まで
間引くが、**間引き幅は全トラックで1つに揃え、間引いたあとの「1点＝何秒か」を
索引に書く**。ここを揃えないと、長い録音で波形が時間軸の先頭に潰れ、長さの
違うトラック同士でも縮尺が食い違う。

## 6. 外部サービスとの付き合い方

| 相手 | 使う機能 | 集約先 |
|---|---|---|
| Groq (LLM) | 会話AI / モデレーション / ニュース要約 / 週次予測 | `services/groq_client.py` |
| Discord API | チャンネル・ロールの一覧（管理画面から） | `webapp_admin/auth.py` |
| P2PQuake | 地震情報（WebSocket） | `services/earthquake_service.py` |
| VirusTotal | URL の検査 | `services/virustotal_service.py` |
| MetalpriceAPI | 貴金属の価格 | `services/metal_service.py` |
| Frankfurter (ECB) | USD/JPY。Stooq は 2026年8月頃から bot 検証が入って CSV を直接取れなくなった | `webapp/forecast_utils.py` |
| Google News RSS | ニュース配信と予測の材料 | `services/news_service.py`, `webapp/forecast_signals.py` |

Groq は API キーを4機能で共有している。呼び出し側同士に調整が無いと、ある
サービスのバーストが他を巻き込んでレート制限（429）を誘発する。そこで
**用途ごと（bucket）に同時実行数と最小呼び出し間隔を制御する共通ラッパー**を
1つ置き、全員がそこを通る。

外から取ってきた URL は `services/url_safety.py` を通す（内部ネットワークへの
リクエストを踏ませないため）。

## 7. 全体を貫く約束

コードの中で繰り返し守っている規則。新しく足すときもここに合わせる。

### 同じ判定を2箇所に書かない

片方だけ直して取りこぼす、が実際に何度も起きた。判定は1つの関数に寄せ、
関連する2つの問い（「開発者パネルは存在するか」と「この人は開発者か」など）が
別々の読み方をしている状態を作らない。

### 設定は読む側まで通す

保存できて画面にも出るのに、送る側が一度も読んでいない、という設定が実際に
あった（録音の通知チャンネル）。設定を足したら、それを**使う**場所まで
繋がっていることを確かめる。`tools/check_admin_schema.py` が経路の一部を
機械的に見る。

### 黙って何もしない分岐を作らない

条件に当たらなかったとき、ファイルだけ消えて「受信」「完了」のログが残り、
何も実行されないまま成功に見える、という状態を避ける。理由を1つに特定して
ログへ残す。シグナルの分岐に `else: 未知のシグナルなので何もしませんでした`
の警告があるのはこのため。

例外を握りつぶすときも、必ず理由を残す。「握りつぶしてよい」と判断した根拠を
コメントに書く。

### 既定は安全側・不明は出さない・不都合も隠さない

- 自動録音の既定はオフ。録音の開始告知は**無効化できない**
- 声の解析は「加工されているか」までしか言わない。「誰か」は出さない（出せない）
- 書き出した録音が雑音になっていないかを測り、疑わしければ Discord の結果と
  ミキサーの両方に印を付ける。落として聞くまで気づけないのでは遅い
- ロールの判定に失敗したときは「バイパスなし」ではなく「判定できなかった」を
  返す。同じ扱いにすると、設定を読めなかっただけで全ロール剥奪まで進む

### 環境変数は envutil を通す

`int(os.environ.get("X", "600"))` は、`X=`（空文字で宣言だけ）や壊れた値で
**インポート時に落ちる**。`Path(os.getenv("SETTINGS_DIR", 既定値))` は空文字だと
`Path("")` = カレントディレクトリになり、書く側と読む側で場所がずれる。
`envutil` の関数はいずれも例外を投げず、理由をログに残して既定値へ倒す。

### イベントループを塞がない

FastAPI のハンドラから重い同期処理（ffmpeg、長い計算）を直接呼ぶと、その
ワーカーが受けている**他のリクエストまで巻き添えで止まる**。`asyncio.to_thread`
へ逃がす。実測で、声の解析（約7秒）を直接呼んでいたときは同時のヘルスチェックが
3.96 秒待たされていた。

## 8. 検証

DB も Discord も要らない範囲で、機械的に確かめられるものは全部確かめる。

```bash
python -m unittest discover -s tests -t .     # 380 件。Discord/ネットワークに触らない
python tools/check_admin_schema.py            # スキーマと services の噛み合わせ
python tools/check_admin_ui.py                # 管理画面を実ブラウザで操作
python tools/check_recording_mixer.py         # 波形の縮尺と再生位置を実ブラウザで
python tools/generate_admin_docs.py --check   # ドキュメントがスキーマと一致するか
python tools/check_requirements.py            # 依存の固定と矛盾
```

いずれも一時ディレクトリを `SETTINGS_DIR` にして動くので、本物の
`settings.json` は変更しない。

テストの書き方の方針:

- **「同じことがまた起きたら落ちる」形で書く**。直したバグには、その症状を
  再現するテストを足す
- 直した内容を外したコピーで、実際にそのテストが落ちることを確かめる。
  落ちないテストは何も守っていない
- ブラウザの中でしか起きないこと（描画、`<audio>` の挙動）は playwright で
  実ブラウザに確かめさせる。ただし**再現できないものは「できない」と書く**。
  たとえば headless Chromium では `<audio>` 同士がほとんど離れないため、
  再生位置のずれは検査で再現できていない

## 9. 分かっている限界

| こと | 内容 |
|---|---|
| シグナルの遅延 | 管理画面からの操作が Bot に届くまで最大30秒 |
| 管理画面の複数ワーカー | メトリクス・監視・レート制限がプロセスローカル。`ADMIN_WORKERS>1` では表示値がズレる（起動時に警告する）。レート制限を共有するには Redis が要る |
| ミキサーの拡大率の下限 | 1px/秒 が下限なので、長い録音は「全体」でも画面に収まりきらない。横スクロールで見る |
| 声の解析 | 話者の同定はできない。RVC のように声質を別人へ置き換える方式からの復元もできない（元の声道特性は破棄されていて逆関数が無い） |
| 録音の縮尺 | 波形は上限 3000 点。6時間なら1点あたり約7秒で、拡大しても粒はそれ以上細かくならない |
